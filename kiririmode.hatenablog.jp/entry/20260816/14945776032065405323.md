AIに「あの件、設計しておいて」と丸投げして、返ってきたのが当たり障りのない一般論だったとき、ムッとして「AIって結局こんなもんか」と思ったこと、ないだろうか。
僕は仕事柄、いろんな人にAIを使って便利になってほしい立場にいる。だから、AIの出力が期待外れだと「AI側の限界」だと誤解されるのを見るたび、正直もったいないなと思う。

原因の多くは、渡すコンテキスト側にあるように見える。AIが悪いんじゃない。渡し方が悪いか、そもそも渡してない。
学習データそのままの一般論しか返ってこないのは、AIが賢くないからではなく、そのAIが今、おまえの組織やプロジェクトの文脈をまだ何ひとつ渡されていないからだったりする。
かつてハッカー文化で言われていたSTFUAWSC (Shut the fxxk up and write some code; 文句や議論は脇に置き、とにかくコードを書け)がある。それをもじって言えば、"Shut the fxxk up and write some context"、まずは黙ってコンテキストを整備しろ、サボるなという話に帰着する。

[https://scrapbox.io/nishio/STFUAWSC:embed]

とはいえ「コンテキストを渡せ」と言われても、何をどう渡せばいいのか、ピンとこない人も多いし、そもそも僕自身がきちんと言語化できていない。コミュニティにおいても、コンテキスト整備のベスプラ・方法論というのはまだ解決を見ていない気がする。加えて、ベスプラがない状況であったとしても、コンテキストの整備自体が労力のいる作業でもある。

別にコードスタイルとかはどうでも良くないけど、どうでもいいんだよ。
お前のプロジェクトの目的は何だ、課題は何だ、これまでの合意形成結果はなんなんだ。それがないと新しく参画してくれたAIちゃんが、その文脈を理解できない。

そこで、僕が最近かかわるプロジェクトでどうやっているかという話になる。議事録ドリブンで頑張っている。

# 議事録を読み返すと、迷子になる

議事録を取るのは本当に楽になった。
取る、というか、だいたいAIが取ってくれる。たいがいのオンラインミーティングツールには録音機能がついており、[wikipedia:WebVTT]だったりが出力できるし、あとはこのトランスクリプトから議事を構成すれば良い。議事録そのものを直接吐き出すツールも山ほどある。
言いたいのは、打ち合わせという場における関係者の表現した意見・議論を文字に落とすコストは極めて安くなったということで。
じゃぁこれをコンテキストとすれば良いよね、からまず始まる。これだけでも価値がある。

ところが議事録というものが、コンテキストとして再利用しやすいかというとそうではない。
議事録は、発言が起きた順番に並んでいる。これは自然なことで、書記係は喋られた順に書き取るしかない。そういう意味ではWeb上の記事とかも似たようなもので、著者が説明しやすい順、あるいは思いついた順に並んでいる。この、記録が並んでいる順番のことを「配列軸」と呼ぶことにする。

後から読み返す・再利用するときに欲しいのは配列軸ではない。欲しいのは「この論点について何を前提にして、何を基準に何を結論としたか、何を捨てたか」というような切り口がほしい。これを「論点軸」と呼ぶ。論点ごとのまとまりにすれば、AIに渡すコンテキストとして効いてくるし使いやすくなる。チャンキングと同じだ。使いやすい単位に切り出したい。

議事録が後になって再利用しづらいのは、情報が足りないからではなく、配列軸と論点軸がズレているからだ。判断の根拠はちゃんと発言として残っている。ただ、それが欲しい形(論点ごとのまとまり)では並んでいない。

これは、時系列という軸が司会や進行の都合で決まっていることが多く、話の内容の論理的なまとまりとは関係がないから起きる。たまたまその順で喋られただけの記録なら、後から論点の切り口で読み直すために並べ替えてしまっても、話の筋は壊れない。

# 転置は並べ替えじゃない

じゃあ議事録を論点ごとに並べ替えれば解決か、というと、そう簡単でもない。この組み替えを「転置」と呼ぶことにするけど、転置は2つの作業を伴う。

## 「なぜそう判断したか」「いつ覆したか」も一緒に運ぶ

時系列という軸は、実は「いつ決まったか」だけでなく「なぜそう判断したか」「一度決めたことをいつ覆したか」という改訂の履歴も担っている。論点ごとに組み替えると、この履歴の置き場所がなくなってしまうケースがある。

だから、時系列を単純に捨てるのではなく、論点ごとの本文の中に「なぜ結論を変えたか」「以前はどう決めていたか」として畳み込んでおく必要がある。この「なぜ」は、意識して書いておかないと消える。ADRと同じだ。

## 誰が読んでもわかる形に書き直す

もうひとつは、自律性を持たせる作業。口頭のやりとりには、指示語や省略された主語、その場にいた人にしか通じない前提が大量に含まれている。「さっきの件」「あれでいきましょう」みたいなやつだ。このままでは、当事者以外には復元できない。

転置では、前提を補って、単体で読んでも意味がわかる形にする必要がある。厄介なのは、この書き直しが正しいかどうかを機械的には判定できないところ。だからここは、AIとの共同作業になる。
考えてみれば、「コンテキストなしにAIへ丸投げする」のとはむしろ逆の作業で、AIに、コンテキストを一緒に作ってもらっている。AIとの同期的な協業になる。この「同期的な協業」は、前に書いたAI委譲の3問(インプット整備・出力検証・合意形成)のフレームのQ2でも触れた話だ。

[https://kiririmode.hatenablog.jp/entry/20260628/14945776032047400112:embed]

# これ、AIとの付き合い方の話でもある

議事録をそのまま渡すやり方は、質問のたびに関連しそうな部分をAIに探させて、毎回ゼロから解釈させることに近い。似た構造は、検索（RAG）でドキュメントをAIに読ませるやり方にもある。mem0のブログ「The State of Agent Wikis」は、この方式の弱点をこう説明している。

[https://x.com/mem0ai/status/2079585032587694582:embed]

> the tenth answer is not better than the first answer. You pay the cost of the work ten times.
>
> 10回目の回答は、1回目の回答より良くなるわけではない。同じ作業のコストを10回払うことになる。
>
> <cite>[The State of Agent Wikis](https://x.com/mem0ai/status/2079585032587694582)</cite>

一方でこの記事が紹介している「`agent wiki`」(LLM Wikiと呼んだ方が通りは良いと思う）という方式は、違う方法を採る。ソースを読み解くコストを、質問のたびにではなく、取り込み(ingest)のときに一度だけ払う。その成果をmarkdownのページとして残しておく。[Andrej Karpathyの元のgist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)を引きながら、記事は「知識は一度コンパイルされ、以後は最新に保たれる。クエリのたびに再導出されるわけではない」という趣旨を紹介している。つまり、蓄積して複利で効いてくる資産になる。一度払ったコストが、あとでずっと効いてくる。

議事録をそのまま渡すのは前者に近い。論点軸に組み替えてナレッジ化しておくのは後者に近い。一度手間をかけて整理しておけば、以後の利用すべてに効いてくる。「AIって結局こんなもんか」の正体はAI側の限界じゃない。渡し方の問題だ。というか、そもそも議事録を取ってないなら取れ、から始まることも多い。

なお、ぼくは論点ごとのmarkdownを切り出した後、他の論点のMarkdownnとの関連をリンクとして繋いで、事実上のLLM Wikiとして構築するようにしている。

# 手間と天井の話

いいことばかり書いたけど、都合の悪い話も書いておく。

## 昇華、実は結構な手間がかかる

正直そこそこ手間がかかる。議事録が溜まるたびに全部これをやろうとすると、たぶん続かない。

僕自身はこの作業をSKILLとして仕組み化した。最初は全部の論点を均等に拾おうとして、あれもこれもと膨らんで収拾がつかなくなったので、「直交したコアな論点を、重要度の高い順に」抽出させるようにしている。それだけで、だいぶ楽になった。プライベートで使っているskillの論点抽出はこんな感じになっている。

> 資料全体から、将来別の文脈でも再利用したい「使えそうな論点」を複数抽出する。1つの資料には通常2〜5件程度の論点が含まれるが、これは目安であり、資料の情報量に応じて増減してよい。ただし、目安の件数を埋めるために独立性を犠牲にしてはならない。各候補について次の2つを用意する。
>
> 仮タイトル: CLAUDE.mdのタイトル指針（「アイデアを直接表現する短く明快なタイトル」）に沿った日本語のタイトル
> 1文の説明: この論点が何を言っているかを、自分の言葉で1文にまとめたもの
> 抽出した候補は、互いに独立していなければならない。これはCLAUDE.mdが定めるZettelkastenの単一性（Atomicity）・自律性（Autonomy）の原則を抽出段階から適用するものであり、次の2条件で確認する。
>
> - 単一性: どの2つの候補も、同じ主張の言い換えではなく、一方が他方の特殊ケース（包含関係）にもなっていない
> - 自律性: どの候補も、他の候補を読まなければ1文説明が理解できないという依存関係を持たない
> 抽出の過程でこれらに反する候補ペアに気づいた場合は、ユーザーに提示する前に統合するか、境界を引き直して独立した候補に分割し直す。この独立性チェックは今回抽出する候補同士（同一バッチ内）を対象とするものであり、既存のevidenceノートとの重複判定（後述2-2）とは別の観点である。
>
> 独立した候補集合が確定したら、各候補に資料内での中心度（その論点が資料の主張にどれだけ近いか。主題そのものを扱う論点が上位、余談・補足的な言及が下位）に基づいて順位をつける。中心度が同等と判断される候補同士は、資料中の登場順を採用する。

## 議事の質が、昇華の質の天井になる

もうひとつ、大事な限界がある。素材が議事録という、いわば二次資料である以上、そこから取り出せる論点の質は、その議事録自体の質を超えられない。

判断基準や、検討した末に捨てた案は、結論だけを書く議事録では真っ先に落ちてしまう。だから、いざ転置しようとしたときに、肝心の「なぜその結論になったか」が議事録のどこにも書かれていない、ということが普通に起きる。

これを防ぐには、議事録を作る段階から、あるいは打ち合わせの段階から、判断基準と却下案をちゃんと残しておくという意識が必要になる。

# 最後に

AIに丸投げして一般論しか返ってこないのは、コンテキストを与えられていないことが原因のケースが多いと思っている。
コンテキストエンジニアリングの前提はコンテキストの蓄積だ。おれたちの頭の中をAIは覗けない。
