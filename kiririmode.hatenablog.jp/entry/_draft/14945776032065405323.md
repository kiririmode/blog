半年前の会議の議事録を開いて、「あれ、なんでこの設計にしたんだっけ」を確かめようとしたことはないだろうか。上から下へ読み進めても、その判断が出てくる発言はどこにあるのかすぐには見つからない。議題と議題のあいだを行ったり来たりしながら、目当ての一言を探し回ることになる。

心当たりがある人は、実はもうひとつ別の場面でも同じことをやっている。AIに「あの件、まとめておいて」と丸投げして、返ってきたのが当たり障りのない一般論だったとき。ムッとして、「AIって結局こんなもんか」と思ったこと、ないだろうか。

このふたつ、原因は同じだと思っている。僕は仕事柄、いろんな人にAIを使って便利になってほしい立場にいる。だから、AIの出力が期待外れだと「AI側の限界」だと誤解されるのを見るたび、正直もったいないなと思う。原因の多くは、渡すコンテキスト側にある。AIが悪いんじゃない。渡し方が悪いだけだ。学習データそのままの一般論しか返ってこないのは、AIが賢くないからではなく、そのAIが今、あなたの組織やプロジェクトの文脈をまだ何ひとつ渡されていないからだ。

とはいえ「コンテキストを渡せ」と言われても、何をどう渡せばいいのか、ピンとこない人も多いと思う。だからこの記事では、身近な「議事録」を材料に、AIに渡せる形へ整える方法の話をしたい。かつてハッカー文化で言われていた "write the fuck up and write some code"(つべこべ言わずに手を動かして書き上げろ)をもじって言えば、"write the f**k up and write some context"、まずは議事録を書くところから始めてみようか、という話だ。

# 議事録を読み返すと、迷子になる

さっきの「探し回る」感覚を、もう少し掘り下げてみたい。

議事録は、発言が起きた順番に並んでいる。これは自然なことで、書記係は喋られた順に書き取るしかない。記事も似たようなもので、著者が思いついた順、あるいは説明しやすい順に並んでいる。この、記録が並んでいる順番のことを「配列軸」と呼ぶことにする。

一方、後から読み返すときに欲しいのは配列軸ではない。「この論点について何を前提にして、何を基準に何を選び、何を捨てたか」という切り口だ。これを「論点軸」と呼ぶ。

議事録が読みにくいのは、情報が足りないからじゃない。配列軸と論点軸がズレているからだ。判断の根拠はちゃんと発言として残っている。ただ、それが欲しい形(論点ごとのまとまり)では並んでいない、というだけの話。

これは、時系列という軸が「偶有的」だから起きる。小難しく言うと「偶有的」な順序、なんだけど、平たく言えば「たまたまその順番になっただけ」ということ。議事の議題順なんて、司会や進行の都合で決まっているだけで、話の内容の論理的な順番とは関係がない。たまたまその順で喋られただけの記録なら、後から論点の切り口で読み直すために並べ替えてしまっても、話の筋は壊れない。

# 転置は並べ替えじゃない

じゃあ議事録を論点ごとに並べ替えれば解決か、というと、そう簡単でもない。この組み替えを「転置」と呼ぶことにするけど、転置は単なる並べ替えではなく、ふたつの作業を伴う。

## 「いつ覆したか」も一緒に運ぶ

時系列という軸は、実は「いつ決まったか」だけでなく「一度決めたことをいつ覆したか」という改訂の履歴も担っている。論点ごとに組み替えると、この履歴の置き場所がなくなってしまう。

だから、時系列を単純に捨てるのではなく、論点ごとの本文の中に「なぜ結論を変えたか」「以前はどう決めていたか」として畳み込んでおく必要がある。gitのdiffと同じで、差分はどの行が変わったかは教えてくれるけど、なぜ変えたのかまでは教えてくれない。この「なぜ」は、意識して書いておかないと静かに消える。

## 誰が読んでもわかる形に書き直す

もうひとつは、自律性を持たせる作業。口頭のやりとりには、指示語や省略された主語、その場にいた人にしか通じない前提が大量に含まれている。「さっきの件」「あれでいきましょう」みたいなやつだ。このままでは、当事者以外には復元できない。

転置では、欠落した前提を補って、単体で読んでも意味がわかる形に書き直す必要がある。厄介なのは、この書き直しが正しいかどうかを機械的には判定できないところ。だからここは、AIが論点の候補と補完案を提示して、人間がその場にいた記憶をもとに判定する、という共同作業になる。

考えてみれば、「コンテキストなしにAIへ丸投げする」のとはむしろ逆の作業だ。AIに、コンテキストを一緒に作ってもらっている。

# これ、AIとの付き合い方の話でもあるんだよね

ここで最初の話に戻る。議事録をそのままAIに渡し続けるのと、論点軸に組み替えてから渡すのとでは、何が違うんだろう。

議事録をそのまま渡すやり方は、質問のたびに関連しそうな部分をAIに探させて、毎回ゼロから解釈させることに近い。似た構造は、検索(RAG)でドキュメントをAIに読ませるやり方にもある。mem0のブログ「The State of Agent Wikis」は、この方式の弱点をこう説明している。

[https://x.com/mem0ai/status/2079585032587694582:embed]

> the tenth answer is not better than the first answer. You pay the cost of the work ten times.
>
> 10回目の回答は、1回目の回答より良くなるわけではない。同じ作業のコストを10回払うことになる。
>
> <cite>[The State of Agent Wikis](https://x.com/mem0ai/status/2079585032587694582)</cite>

一方でこの記事が紹介している「`agent wiki`」という方式は、違う発想を採る。ソースを読み解くコストを、質問のたびにではなく、取り込み(ingest)のときに一度だけ払う。その成果をmarkdownのページとして残しておく。[Andrej Karpathyの元のgist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)を引きながら、記事は「知識は一度コンパイルされ、以後は最新に保たれる。クエリのたびに再導出されるわけではない」という趣旨を紹介している。つまり、蓄積して複利で効いてくる資産(persistent, compounding artifact)になる。一度払ったコストが、あとでずっと効いてくるということだ。

議事録をそのまま渡すのは前者に近い。論点軸に組み替えてナレッジ化しておくのは後者に近い。一度手間をかけて整理しておけば、以後の質問すべてに効いてくる。「AIって結局こんなもんか」の正体は、たぶんこれだ。AI側の限界じゃない。渡し方の問題だ。

# 手間と天井の話

いいことばかり書いたけど、都合の悪い話も正直に書いておく。じゃないとこの記事自体が、コンテキストの伴わない一般論になる。それはさすがに洒落にならない。

## 昇華、実は結構な手間がかかる

さっき書いたふたつの作業(改訂履歴の畳み込みと、自律性の付与)は、正直そこそこ手間がかかる。議事録が溜まるたびに全部これをやろうとすると、たぶん続かない。

僕自身はこの作業をSKILLとして仕組み化した。最初は全部の論点を均等に拾おうとして、あれもこれもと膨らんで収拾がつかなくなった。だから今は、「互いに独立したコアな論点を、重要度の高い順に」抽出させる、という一言をプロンプトに足しただけ。それだけで、だいぶ楽になった。

## 議事の質が、昇華の質の天井になる

もうひとつ、大事な限界がある。素材が議事録という、いわば二次資料である以上、そこから取り出せる論点の質は、その議事録自体の質を超えられない。

判断基準や、検討した末に捨てた案は、結論だけを書く議事録では真っ先に落ちてしまう。だから、いざ転置しようとしたときに、肝心の「なぜその結論になったか」が議事録のどこにも書かれていない、ということが普通に起きる。

これを防ぐには、議事録を作る段階から、判断基準と却下案をちゃんと残しておく、という意識が必要になる。

## 順番自体に意味があるものは、転置しちゃいけない

最後にもうひとつ。今回の話は、あらゆる記録に当てはまるわけではない。手順書や、数学の証明、物語みたいに、順番そのものが意味を持つものは、転置してはいけない。レシピの手順を論点ごとにバラバラに並べ替えたら、それはもう料理の手順として成立しなくなる。並び順がたまたまなのか、それとも順番自体に意味があるのかは、最初に見極めておく必要がある。

# 最後に

議事録を読み返して迷子になるのも、AIに丸投げして一般論しか返ってこないのも、原因は同じところにあると思う。記録が並んでいる順番と、後から欲しい切り口が、噛み合っていないだけだ。

だから、判断基準と却下案を残す形で、まず議事録を取ることから始めてみないか。そのうえで、それを論点ごとに組み替えてナレッジまで昇華しておけば、AIとのやりとりはたぶん今よりずっと捗ると思う。その昇華の作業自体も、AIに手伝ってもらえる。

write the f**k up and write some context。まずは、そこからだ。
